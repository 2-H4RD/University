## Подготовка в Android Studio

1. File → Open → выберите эту папку Lesson7, дождитесь Gradle Sync. Встроенный Gradle JDK: Android Studio jbr. SDK: установленная платформа Android 35.
2. Device Manager → Pixel_9, Android 15/API 35 → Run. При зависшем снимке используйте Cold Boot, без удаления данных.
3. В списке Run выберите `Verify Lesson7`: это assembleDebug, lintDebug и testDebugUnitTest. Затем `Device Tests Lesson7` выполняет installDebug и :UITests:connectedDebugAndroidTest на реальном Android AVD. Не запускайте два набора UI одновременно на одном устройстве.
4. Для демонстрации отдельной программы выберите её Android App конфигурацию и Run. APK каждого модуля находится в build/outputs/apk/debug; MireaProject включён в общий проект и может открываться отдельно.
5. Build Success подтверждает сборку; успех демонстрации подтверждается действиями и результатами приложения. NO-SOURCE у JVM-тестов не считается выполненным практическим сценарием.

## Как читать проект

`settings.gradle.kts` включает модули. `applicationId` — пакет установленного APK; `namespace` — пакет R и Binding, они могут отличаться у снимков MireaProject. Manifest объявляет launcher, разрешения и компоненты. `res/layout` описывает View, `res/values` — строки и тему; ViewBinding генерирует ссылки по android:id. `MainActivity.onCreate` создаёт UI и callbacks. `BaseActivity.frame` учитывает системные Insets, `io` — Executor для долгой работы, `ui` доставляет изменение View в главный поток и проверяет актуальность Activity. `LabFragment` делает аналогичное для фрагмента и освобождает binding в onDestroyView. Сгенерированные Binding/R/Room-классы и каталоги build не являются вручную написанным предметным кодом.

Для каждого экрана на защите покажите цепочку: XML ID → поле binding/локальная переменная → слушатель кнопки → проверка данных → фоновая или системная операция → callback → видимый результат. Перед ответом о переменной найдите её объявление и все использования в Android Studio: Go to Declaration и Find Usages.

## TimeService · страницы PDF 11–13

**Задание:** Настоящий Socket time.nist.gov:13, разбор ответа, отдельные поля даты/времени.

Нажмите получение времени. io открывает настоящий Socket к time.nist.gov, порт 13 (Daytime), connect/read имеют таймаут по 10 секунд. BufferedReader читает ASCII и пропускает пустые строки. Matcher находит YY-MM-DD и HH:MM:SS; дата дополняется 20, поля date/time подписаны UTC. raw сохраняет исходный ответ для проверки. finally снова включает кнопку. Покажите в отчёте реальный ответ или точную сетевую ошибку. Если порт 13 закрыт сетью, это ограничение среды: часы устройства либо HTTPS-время не подставляются как успешный Socket. При тестировании без сети UI должен оставаться отзывчивым.

**Что предъявить:** Сетевой ответ NIST и UTC; timeout/недоступная сеть фиксируются как ограничения, не успех. Сопоставьте с фактическим статусом в отчёте, не объявляйте недоступную интеграцию проверенной.

## HttpURLConnection · страницы PDF 13–17

**Задание:** Внешний IP, отдельные поля города/региона/страны/координат; эти координаты передаются Open-Meteo.

ConnectivityManager сначала проверяет наличие INTERNET capability. NetworkClient разрешает только HTTPS, проверяет HTTP 200, ограничивает ответ 1 МБ, задаёт connect/read timeout и disconnect в finally. JSON от ipwho.is даёт IP/город/регион/страну/latitude/longitude. Эти же фактические координаты форматируются с Locale.ROOT в URL Open-Meteo: десятичная точка обязательна для запроса. current_weather содержит temperature/windspeed/weathercode/time. Каждое географическое поле отдельное. Покажите реальные ответы и погоду; IP-геолокация приблизительна и не является GPS. Сетевая ошибка отображается явно, кнопка возвращается в доступное состояние. Исключения не превращаются в заранее заполненные погодные значения.

**Что предъявить:** Живые HTTPS ответы, JSON поля, фактическая погода, ошибки/нет сети. Сопоставьте с фактическим статусом в отчёте, не объявляйте недоступную интеграцию проверенной.

## FirebaseAuth · страницы PDF 20–28

**Задание:** Реальное Firebase Email/Password; регистрация, верификация письма, вход, выход; UI по состоянию; скрины приложения и Firebase console в raw.

Сначала выполните ПОДКЛЮЧЕНИЕ_СЕРВИСОВ.md. AuthConfig.get инициализирует настоящий FirebaseApp из ресурсов google-services.json и возвращает FirebaseAuth; без конфигурации вход/регистрация отключены с объяснением. authenticate проверяет email и длину пароля, затем выбирает createUserWithEmailAndPassword либо signInWithEmailAndPassword. Task асинхронный, addOnCompleteListener(this,...) привязан к Activity. refresh читает getCurrentUser и переключает видимость входа/выхода/проверки. UID — идентификатор аккаунта, а isEmailVerified — состояние подтверждения; создание аккаунта само по себе письмо не подтверждает. verify вызывает sendEmailVerification, reload обновляет состояние после перехода по ссылке. После операции пароль очищается. signOut удаляет локальную сессию, не пользователя в облаке. На защите UID в приложении должен совпасть с записью Authentication → Users; реальные скрины поместите в res/raw. Явный debug-параметр эмулятора проверяет SDK локально, но не заменяет облачную консоль.

**Что предъявить:** SDK/облачный проект пользователя; новый тестовый пользователь; письмо; UID совпадает с консолью. Сопоставьте с фактическим статусом в отчёте, не объявляйте недоступную интеграцию проверенной.

## MireaProject · страницы PDF 30

**Задание:** Firebase-вход как launcher, переход на главный экран после входа; фрагмент сетевого ресурса.

LoginActivity — launcher; после успешного входа afterSignIn открывает MainActivity и закрывает экран входа. MainActivity дополнительно проверяет текущего пользователя и возвращает на вход при отсутствии сессии; android:exported=false не позволяет посторонним приложениям напрямую запускать главный экран. «Сетевой ресурс» запрашивает настоящую погоду у кампуса через NetworkClient в io. «Аккаунт» показывает Email/UID, отправляет проверку и выполняет signOut с возвратом в LoginActivity. Проверьте новый вход, повторный запуск с сохранённой сессией, выход и невозможность попасть назад в закрытый экран. Для этого приложения нужен отдельный Android-клиент Firebase с его applicationId; JSON другого пакета не подходит.

**Что предъявить:** Закрытый главный экран не обходит вход; авторизация/выход; живая погода. Сопоставьте с фактическим статусом в отчёте, не объявляйте недоступную интеграцию проверенной.

## Ответы на общие вопросы

- **Почему не выполнять всё в onCreate/UI callback?** Главный поток обрабатывает ввод и кадры. Долгий I/O/ожидание задерживает интерфейс; отдельный Thread, Executor, Worker или асинхронный SDK отделяет ожидание, а результат возвращается в UI.
- **Почему нельзя хранить View навсегда?** Activity пересоздаётся при конфигурационных изменениях, View фрагмента уничтожается отдельно. Bundle/Preferences/Room/WorkManager хранят разные виды состояния; binding относится только к текущей View.
- **Что означает final?** Ссылку нельзя переназначить; состояние объекта по ней может изменяться. Значения, захватываемые лямбдой, должны быть final либо effectively final.
- **Что делает try-with-resources?** Гарантирует close для потока/Socket при нормальном выходе и исключении. finally используется для disconnect/восстановления кнопки.
- **Чем dp отличается от sp?** dp масштабирует размеры по плотности, sp дополнительно учитывает настройку размера шрифта. wrap_content измеряет содержимое, match_parent занимает доступную область, weight распределяет остаток.
- **Зачем проверять отказ/отмену/поворот?** Это обычные действия Android, а не редкие аварии. Код должен сохранить корректное состояние, показать причину и не подменять неудачу успехом.
- **Где результаты тестов?** В UITests/build/outputs/androidTest-results/connected/debug (JUnit XML), UITests/build/reports/androidTests/connected/debug (HTML), модульных build/reports/lint-results-debug.* и приложенных материалах verification. Скриншот подтверждает конкретный момент; assertion проверяет конкретное условие, ни один не доказывает всё приложение.
