## Подготовка в Android Studio

1. File → Open → выберите эту папку Lesson5, дождитесь Gradle Sync. Встроенный Gradle JDK: Android Studio jbr. SDK: установленная платформа Android 35.
2. Device Manager → Pixel_9, Android 15/API 35 → Run. При зависшем снимке используйте Cold Boot, без удаления данных.
3. В списке Run выберите `Verify Lesson5`: это assembleDebug, lintDebug и testDebugUnitTest. Затем `Device Tests Lesson5` выполняет installDebug и :UITests:connectedDebugAndroidTest на реальном Android AVD. Не запускайте два набора UI одновременно на одном устройстве.
4. Для демонстрации отдельной программы выберите её Android App конфигурацию и Run. APK каждого модуля находится в build/outputs/apk/debug; MireaProject включён в общий проект и может открываться отдельно.
5. Build Success подтверждает сборку; успех демонстрации подтверждается действиями и результатами приложения. NO-SOURCE у JVM-тестов не считается выполненным практическим сценарием.

## Как читать проект

`settings.gradle.kts` включает модули. `applicationId` — пакет установленного APK; `namespace` — пакет R и Binding, они могут отличаться у снимков MireaProject. Manifest объявляет launcher, разрешения и компоненты. `res/layout` описывает View, `res/values` — строки и тему; ViewBinding генерирует ссылки по android:id. `MainActivity.onCreate` создаёт UI и callbacks. `BaseActivity.frame` учитывает системные Insets, `io` — Executor для долгой работы, `ui` доставляет изменение View в главный поток и проверяет актуальность Activity. `LabFragment` делает аналогичное для фрагмента и освобождает binding в onDestroyView. Сгенерированные Binding/R/Room-классы и каталоги build не являются вручную написанным предметным кодом.

Для каждого экрана на защите покажите цепочку: XML ID → поле binding/локальная переменная → слушатель кнопки → проверка данных → фоновая или системная операция → callback → видимый результат. Перед ответом о переменной найдите её объявление и все использования в Android Studio: Go to Declaration и Find Usages.

## app · страницы PDF 6–7

**Задание:** SensorManager.getSensorList(TYPE_ALL), список названий/диапазонов датчиков.

SensorManager запрашивается системным сервисом, getSensorList(TYPE_ALL) возвращает реальные доступные датчики конкретного устройства. Цикл формирует для каждого Map с name/detail, где detail включает type, maximumRange и vendor. SimpleAdapter связывает эти ключи с двумя TextView стандартной строки ListView. summary показывает количество. Это список возможностей, а не поток измерений. Пустой список на оборудовании без датчиков допустим; на выбранном AVD должны быть реальные строки. Объясните отличие списка всех сенсоров от getDefaultSensor(TYPE_ACCELEROMETER).

**Что предъявить:** Непустой ListView на эмуляторе. Сопоставьте с фактическим статусом в отчёте, не объявляйте недоступную интеграцию проверенной.

## Accelerometer · страницы PDF 8–13

**Задание:** Текущие XYZ ускорения, SensorEventListener, регистрация onResume/отмена onPause.

Откройте Extended Controls эмулятора → Virtual sensors и измените положение. X/Y/Z в м/с² должны меняться, включая составляющую земного притяжения. manager — SensorManager, sensor — акселерометр; при его отсутствии показано сообщение. onResume регистрирует this как SensorEventListener с SENSOR_DELAY_UI; onPause снимает подписку для экономии ресурсов и отсутствия скрытых обновлений. event.values[0..2] — три оси системы координат устройства, не GPS. String.format задаёт три десятичных знака, status подтверждает полученный SensorEvent. onAccuracyChanged оставлен как обязательный callback интерфейса; пустое тело означает, что отдельный UI точности не нужен.

**Что предъявить:** Изменение виртуального датчика и отображаемых значений. Сопоставьте с фактическим статусом в отчёте, не объявляйте недоступную интеграцию проверенной.

## Camera · страницы PDF 14–23

**Задание:** Запрос разрешения, системная камера, FileProvider/EXTRA_OUTPUT, файл в папке приложения и ImageView, Binding.

Нажмите фотографирование и ответьте на runtime запрос камеры. FileProvider превращает файл Pictures/photo_*.jpg в content Uri с ограниченной выдачей прав. authorities использует applicationId, а xml/paths разрешает только Pictures, не весь диск. TakePicture передаёт этот Uri системному приложению как EXTRA_OUTPUT: результатом является boolean, а оригинал лежит в файле. pendingPath относится к текущей съёмке, photoPath — к последнему успешному снимку; отмена не заменяет успешное фото. showPhoto сначала читает только размеры BitmapFactory.Options.inJustDecodeBounds, затем декодирует уменьшенное превью с inSampleSize для памяти. В status остаются размеры оригинала и путь. Перезапустите и поверните экран; выбранный путь хранится в Preferences и Bundle. Сравните оригинал JPEG в Device Explorer и превью ImageView; это разные размеры данных.

**Что предъявить:** Отказ/разрешение/отмена; настоящий JPEG, полные размеры, перезапуск и поворот. Сопоставьте с фактическим статусом в отчёте, не объявляйте недоступную интеграцию проверенной.

## AudioRecord · страницы PDF 24–30

**Задание:** MediaRecorder и MediaPlayer, запись/воспроизведение, взаимное исключение кнопок, №/группа на записи.

Кнопка записи содержит номер 5 и группу БИСО-02-22. Разрешение RECORD_AUDIO запрашивается только при записи. recordFile — Music/voice_note.3gp в каталоге приложения; recorder пишет MIC → THREE_GPP → AMR_NB. prepare настраивает кодек/файл, start начинает захват. recording/playing описывают взаимоисключающие состояния, updateButtons запрещает проигрывание во время записи и запись во время воспроизведения. stopRecording обрабатывает слишком короткую запись: stop может бросить RuntimeException, тогда повреждённый файл удаляется. player читает готовый файл; completion освобождает его и возвращает кнопки. onStop завершает запись и проигрывание. Сделайте запись длиннее секунды, воспроизведите, покажите реальный размер 3GP в Device Explorer. Не выдавайте тишину виртуального микрофона за проверку качества речи физического устройства.

**Что предъявить:** Отказ/разрешение микрофона; размер/длительность файла, воспроизведение, остановка/фон. Сопоставьте с фактическим статусом в отчёте, не объявляйте недоступную интеграцию проверенной.

**Что предъявить:** Уровень для фото документа, фото с описанием инцидента, голосовая заметка с описанием. Сопоставьте с фактическим статусом в отчёте, не объявляйте недоступную интеграцию проверенной.

## Ответы на общие вопросы

- **Почему не выполнять всё в onCreate/UI callback?** Главный поток обрабатывает ввод и кадры. Долгий I/O/ожидание задерживает интерфейс; отдельный Thread, Executor, Worker или асинхронный SDK отделяет ожидание, а результат возвращается в UI.
- **Почему нельзя хранить View навсегда?** Activity пересоздаётся при конфигурационных изменениях, View фрагмента уничтожается отдельно. Bundle/Preferences/Room/WorkManager хранят разные виды состояния; binding относится только к текущей View.
- **Что означает final?** Ссылку нельзя переназначить; состояние объекта по ней может изменяться. Значения, захватываемые лямбдой, должны быть final либо effectively final.
- **Что делает try-with-resources?** Гарантирует close для потока/Socket при нормальном выходе и исключении. finally используется для disconnect/восстановления кнопки.
- **Чем dp отличается от sp?** dp масштабирует размеры по плотности, sp дополнительно учитывает настройку размера шрифта. wrap_content измеряет содержимое, match_parent занимает доступную область, weight распределяет остаток.
- **Зачем проверять отказ/отмену/поворот?** Это обычные действия Android, а не редкие аварии. Код должен сохранить корректное состояние, показать причину и не подменять неудачу успехом.
- **Где результаты тестов?** В UITests/build/outputs/androidTest-results/connected/debug (JUnit XML), UITests/build/reports/androidTests/connected/debug (HTML), модульных build/reports/lint-results-debug.* и приложенных материалах verification. Скриншот подтверждает конкретный момент; assertion проверяет конкретное условие, ни один не доказывает всё приложение.
