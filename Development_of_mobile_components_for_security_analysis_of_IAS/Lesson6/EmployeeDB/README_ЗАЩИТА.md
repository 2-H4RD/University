# EmployeeDB · практика 6

Проверка новой логики запускается в Android Studio конфигурацией **EmployeeDB Tests** на отдельном тестовом AVD. Она выполняет сборку, Lint и два инструментальных сценария. В миграционном сценарии создаётся отдельная временная база, проверяются однократный сброс версии 1 и сохранение ручных ID в версии 2.

**Требование:** Room: Entity/DAO/Database/Application, вымышленные супергерои, CRUD.

ID героя пользователь вводит вручную. @PrimaryKey обеспечивает уникальность, INSERT IGNORE возвращает -1 при конфликте и сохраняет прежнюю запись. Проверки идут по порядку: пустое поле → целое число long → больше нуля → свободный ID. Причина отказа видна рядом с ID и в области результата. Пустое имя или способность также отклоняются. change фиксирует ID в target и в фоне вызывает getById, затем insert с hero.id = target. Поиск, изменение и удаление работают с тем же введённым ID. Успех каждой операции выводится над актуальным списком. После удаления разрешено снова использовать освободившийся ID. AppDatabase имеет версию 2. По просьбе пользователя миграция RESET_1_2 однократно очищает прежнюю таблицу версии 1 и создаёт heroes без AUTOINCREMENT. Обычные повторные запуски версии 2 сохраняют записи. App создаёт один объект Room на процесс, запросы выполняются в io, результат возвращается через ui. Для защиты покажите все ошибки, добавление ID 42, отказ повторной вставки 42, изменение, перезапуск, удаление и повторное использование 42.
