# Модель безопасности

## Доверенные компоненты

ОС, локальный администратор PostgreSQL, исходники, зависимости и Windows-учётная
запись процесса доверенные. Пользователи внутри приложения, имена файлов,
содержимое документов и архивов недоверенные.

Консольный вариант предназначен для учебной демонстрации и работы доверенного
оператора Windows с разделением пользователей внутри приложения.
Он не изолирует учётные записи приложения от человека, который может читать
память процесса, секреты или изменять исходники под тем же Windows SID.
Администратор PostgreSQL может отключить ограничения БД; администратор ОС может
получить доступ к файлам и ключу. Для независимых недоверенных пользователей
нужен сервер под отдельной учётной записью с закрытым доступом к его файлам.

## Меры

* SQLAlchemy/psycopg передают значения отдельно от SQL. Идентификаторы миграций
  и bootstrap формируются через psycopg.sql.Identifier из фиксированных имён.
* Рабочая роль не владеет схемой, не может стать владельцем, менять схему,
  создавать таблицы в public, менять/удалять/очищать аудит или менять audit_head.
* Пароли приложения: Argon2id, память 64 МиБ, 3 прохода, параллелизм 2;
  соль и параметры входят в строку хеша. Проверка через библиотечный API.
* Единый ответ при неизвестном логине/неверном пароле, dummy-хеш, ограничения
  повторных попыток с состоянием в БД. Пять ошибок за пять минут включают
  минутную блокировку логина; общий бюджет — 100 ошибок за пять минут.
  Старая информация об ошибках очищается через сутки.
* Сессия только в памяти. При каждом действии проверяются активность и версия
  аутентификации. Смена пароля отзывает все сессии; деактивация отзывается при
  следующем действии. Веб-cookie и HTTP-токены в консольной архитектуре отсутствуют.
* Авторизация в сервисах: запросы файлов включают owner_id. Существование чужого
  и отсутствующего UUID не различается. Общий аудит доступен только администратору.
* Физические имена — внутренние UUID; пользовательские имена не используются
  в objects/staging. Имена нормализуются в NFC, сравнение для уникальности
  нечувствительно к регистру. Проверяются Windows-имена, ADS, UNC/device-пути,
  точки/пробелы в конце, управляющие и bidi-символы.
* На Windows каталоги-предки открываются и удерживаются без FILE_SHARE_DELETE.
  Reparse points отвергаются по информации открытого handle. Обычные файлы
  открываются с OPEN_REPARSE_POINT; проверяются фактический путь, тип и число
  жёстких ссылок. Уникальное создание не перезаписывает существующий файл.
* На NTFS корень данных и секреты получают защищённую DACL только для текущего SID
  и SYSTEM. Фактический диск D: — exFAT, без persistent ACL; это определяется
  через Windows API, фиктивная гарантия DACL не заявляется.
* Пароли подключения и ключи защищены user-bound Windows DPAPI. Внутренние
  объекты зашифрованы AES-256-GCM: случайный 96-битный nonce для каждой записи,
  UUID объекта входит в AAD. Подмена ciphertext или перенос под другой UUID
  не проходит проверку тега. Ключ AES хранится только в DPAPI-обёртке.
  Вручную импортированные и явно экспортированные копии не шифруются приложением.
* JSON/XML/ZIP обрабатываются в дочернем процессе, который ждёт установки
  ограничения Windows Job Object. Есть лимит памяти и тайм-аут с завершением
  дочернего процесса. Секреты FM_* удаляются из окружения обработчика.
* XML: явные forbid_dtd/forbid_entities/forbid_external; запрет XInclude.
  JSON: запрет дублей и нечисловых чисел, ограничение структуры.
* ZIP: предварительная проверка всех имён, типов, коллизий, размеров и количества;
  затем потоковое чтение с фактическим подсчётом байтов и CRC. Извлечение
  возвращает данные приложению, а не записывает имена архива в файловую систему.
  Автоматической обработки вложенных архивов нет. AES-256 реализован pyzipper.
* Помимо AEAD-тега проверяется SHA-256 расшифрованного содержимого относительно
  метаданных БД.
* Консоль экранирует управляющие последовательности, ограничивает ввод и вывод.
  Shell-команды с пользовательскими значениями отсутствуют.

## Согласованность диска и БД

Единую ACID-транзакцию для PostgreSQL и NTFS приложение не заявляет.
Изменяемые данные публикуются как новый неизменяемый объект:

1. Захватывается транзакционная advisory-блокировка писателей.
2. Проверяются владелец, версия, пространство имён и квота.
3. Содержимое пишется в staging, выполняются flush/fsync.
4. Объект атомарно переименовывается под новым UUID в objects.
5. В одной транзакции БД обновляются метаданные и подписанный аудит.
6. После commit старые неподключённые объекты могут быть удалены.

При аварии до commit новая версия остаётся сиротой, старые метаданные продолжают
указывать на старое содержимое. Очистка при запуске под той же блокировкой
удаляет только неподключённые UUID и временные файлы. Это также покрывает аварию,
при которой строка storage_jobs не успела закоммититься.
При удалении сначала фиксируется отметка удаления и событие, затем убираются байты.
Метаданные удалённого файла остаются для сохранения FK и истории.

Блокировка писателей глобальная: это сознательный выбор для небольшого учебного
приложения, упрощающий межпроцессную согласованность и квоты.
Проверка expected_version не позволяет незаметно перезаписать чужое обновление.

Экспорт имеет предварительно зафиксированное намерение EXPORT_INTENT,
эксклюзивное создание файла и отдельное событие завершения.
После аварии между этими этапами экспортированная копия может существовать
без события завершения; намерение сохраняется. Исходный управляемый файл цел.
Нехватка места/потеря соединения после commit также может требовать проверки
состояния перед повтором команды.

## Аудит

append_event — SECURITY DEFINER с фиксированным search_path.
PUBLIC не имеет EXECUTE; fm_app имеет только вызов добавления и SELECT.
Последовательность и предыдущая подпись проверяются под блокировкой audit_head.
HMAC-SHA256 покрывает канонический payload, номер, время, пользователя,
файл, действие, результат, причину, request_id, снимок метаданных и предыдущий HMAC.
Verifier сравнивает также отдельные колонки БД с подписанным payload.

Ключ не находится в БД и на диске защищён DPAPI. Аудит, checkpoint и throttle
имеют различные HMAC domain prefixes, исключая использование одного протокола
как MAC-оракула для другого. Checkpoint вне БД содержит номер и последний HMAC,
защищён собственным HMAC и обновляется под общей блокировкой аудита.
Отсутствие checkpoint при непустой истории приводит к отказу.
Это выявляет изменение, перестановку и удаление событий, а также усечение
конца ниже последней сохранённой контрольной точки.
Записи, успевшие закоммититься непосредственно перед аварией и ещё не попавшие
в checkpoint, не имеют внешнего подтверждения. Для защиты от администратора БД
и надёжного обнаружения любого отката потребовалось бы внешнее доверенное
append-only хранилище. Локальный checkpoint эту гарантию не заменяет.

Отказы доступа и ошибки проверок сохраняются отдельной транзакцией.
При недоступности аудита изменение метаданных не подтверждается.
После успешного commit ошибка обновления checkpoint может вернуть ошибку команды;
перед повтором требуется посмотреть фактическое состояние.

## Резервирование и зависимости

Резервировать БД, содержимое и ключи/checkpoint нужно согласованно при остановленных
экземплярах. DPAPI требует того же Windows-профиля при восстановлении;
автоматический перенос между профилями не реализован.
Шифруется содержимое внутренних объектов, а не весь диск, метаданные БД,
имена в БД или экспортированные пользователем копии.
exFAT не обеспечивает изоляцию от удаления файлов другим субъектом с доступом
к диску; криптография защищает содержимое и обнаруживает подмену.

requirements.lock фиксирует исполняемые зависимости; requirements-dev.lock
фиксирует полный набор Python-инструментов. Нативный Semgrep и его DLL имеют
отдельный manifest с версиями, SHA-256 и upstream LICENSE. Python-обёртка с
ненужными MCP/OpenTelemetry-зависимостями удалена. Статические проверки не являются
доказательством отсутствия всех уязвимостей; атакующие тесты проверяют конкретные
обещанные свойства. Исключение Bandit B105 относится к запрету значения
административного пароля, а не к хранению действующего секрета в исходниках.
Исключения B404/B603 в scripts/scan_semgrep.py относятся только к запуску
комплектного нативного анализатора после проверки SHA-256: абсолютный путь,
список аргументов, shell=False по умолчанию, конечные лимиты памяти/времени.
