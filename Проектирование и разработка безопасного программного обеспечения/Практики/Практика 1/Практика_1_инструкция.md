## 1. Цель, задания и порядок выполнения

Цель работы — найти SQL-инъекцию в учебном веб-приложении, объяснить её причину, устранить уязвимость и сравнить поведение исходного и исправленного обработчиков.

| Задание | Что необходимо сделать | Подтверждение в отчёте |
|---|---|---|
| 1 | Обнаружить SQL-инъекцию статическим анализатором в модуле Blind SQL Injection | Код, правило анализатора, фактическая находка и цепочка движения данных |
| 2 | Провести кодревью и описать слабые места | Разбор причины, механизма эксплуатации, последствий и мер защиты |
| 3 | Реализовать безопасный вывод информации об объекте | Исправленный код, объяснение защиты, таблица испытаний |
| 4 | Найти уязвимость с помощью sqlmap | Проверяемый запрос, команда запуска, подтверждённые параметр и тип инъекции |
| 5 | Найти уязвимость с помощью Burp Suite | Контрольные запросы, ответы, статусы и сравнение истинного и ложного условий |

Основной вариант задания 3 в этой инструкции — исправить уже существующий обработчик DVWA, сохранив штатный вход в приложение и поиск по GET-параметру `id`. Отдельная новая страница с собственной формой входа для этого варианта не требуется.

Рекомендуемый порядок фактических экспериментов:

1. Подготовить исходный уязвимый стенд.
2. Выполнить задания 1 и 2.
3. Выполнить задания 4 и 5 на исходном коде.
4. Выполнить задание 3: заменить обработчик защищённым.
5. Повторить проверки sqlmap и Burp на исправленном коде.

Разделы документа расположены по номерам заданий, но указанный порядок удобнее для экспериментов: после исправления уязвимость перестанет воспроизводиться. Переключение уровня на Low **не возвращает исходный код**, если файл Low уже отредактирован.

Приведённые далее результаты являются ожидаемыми, а не автоматически полученными на любом компьютере. В отчёт переносите только собственные наблюдения.

## 2. Подготовка стенда

### 2.1. Что потребуется

- Работающий локальный DVWA с MySQL или MariaDB.
- Браузер с инструментами разработчика.
- Доступ к исходникам DVWA и редактор текста для задания 3.
- Semgrep Playground для статического анализа в браузере.
- Python 3 и sqlmap для задания 4.
- Burp Suite Community Edition для задания 5.
- PowerShell для команд, приведённых в инструкции.

Задания 1 и 2 можно выполнить в браузере: исходный код открывается через кнопку DVWA, а статический анализ выполняется в Playground. Задание 3 требует изменения серверного файла. Для задания 4 используется отдельный инструмент, для задания 5 — Burp Suite. Поэтому всю практическую работу выполнить только обычными вкладками браузера нельзя.

Docker не является обязательным условием заданий. При штатной установке PHP, веб-сервера и СУБД действия в интерфейсе DVWA и проверяемые запросы остаются теми же; отличаются запуск сервера и расположение рабочего проекта.

### 2.3. Вход и выбор уровня

1. Откройте `http://127.0.0.1:4280/`.
2. Войдите в DVWA. Для неизменённой учебной установки стандартная пара — `admin` / `password`. Если она изменена, используйте свою.
3. Откройте **DVWA Security**.
4. В поле уровня выберите **Low**, нажмите **Submit**.
5. Откройте **SQL Injection (Blind)**.
6. Проверьте адрес: `/vulnerabilities/sqli_blind/`.
7. Внизу страницы проверьте уровень Low и используемую СУБД MySQL.

Не путайте **SQL Injection** и **SQL Injection (Blind)**: в этой работе исследуется именно второй модуль.

Не нажимайте **Create / Reset Database** для обычной проверки: сброс изменяет учебные данные и может уничтожить результаты предыдущих экспериментов. Инициализация нужна только для ещё не настроенной базы.

Если стенд развёрнут через Docker Compose, запустите Docker и выполните из корня проекта:

```powershell
docker compose up -d
docker compose ps
```

Для уже установленного стенда это запуск, а не повторная установка. Проверьте, что порт опубликован только на локальном интерфейсе. При нативной установке запустите свои веб-сервер и СУБД штатным способом.

### 2.4. Контрольные запросы до исправления

Для каждого значения вводите только текст из таблицы в поле **User ID**, затем нажимайте **Submit**.

| Значение | Ожидаемый результат исходного Low |
|---|---|
| `1` | `User ID exists in the database.` при наличии пользователя 1 |
| `999999` | `User ID is MISSING from the database.`, если такой записи нет |
| `1' AND '1'='1` | Сообщение о существующей записи |
| `1' AND '1'='2` | Сообщение об отсутствии записи |

Используйте обычный прямой апостроф `'`, не типографские кавычки. Дополнительный апостроф в конце строк из таблицы не нужен: закрывающая кавычка уже присутствует в SQL-шаблоне приложения.

Если пользователь с ID 1 отсутствует, сначала найдите существующий числовой ID и используйте его во всей контрольной паре. Для отсутствующего ID также выберите значение, которого действительно нет.

Чтобы увидеть HTTP-статус:

1. Нажмите **F12**.
2. Откройте **Network / Сеть**.
3. Отправьте значение формы.
4. Выберите запрос к `sqli_blind` и посмотрите **Status Code**.

В типичном исходном обработчике DVWA отсутствие записи сопровождается HTTP 404. Сам по себе 404 не доказывает неисправность сервера: важно, какой запрос вызвал ответ. Страница входа вместо модуля означает проблему с авторизацией, а не результат SQL-проверки.

Эта ручная проверка помогает понять Blind SQLi, но **не заменяет статический анализатор** из задания 1.

## 3. Задание 1. Обнаружение SQL-инъекции статическим анализом

### 3.1. Откройте фактически выполняемый исходный код

1. Убедитесь, что открыт **SQL Injection (Blind)** и выбран Low.
2. Нажмите кнопку **View Source** внизу страницы DVWA.
3. Посмотрите PHP-код уровня Low.
4. Найдите получение значения `id` из `$_GET`.
5. Найдите построение SQL-запроса со вставкой этого значения.
6. Найдите вызов функции выполнения запроса.

Не используйте обычное **«Просмотреть код страницы» / Ctrl+U** вместо **View Source**. Ctrl+U показывает HTML, уже сформированный сервером, а не исполняемый PHP.

В MySQL-ветке исходного обработчика нужно увидеть три звена:

- источник данных: `$_GET['id']`;
- построение строки запроса с пользовательским значением внутри условия `WHERE`;
- выполнение через `mysqli_query`.

Имена промежуточных переменных и номера строк могут отличаться между версиями. В отчёте указывайте номера строк **своего** файла.

### 3.2. Запустите Semgrep в браузере

1. Откройте [Semgrep Playground](https://semgrep.dev/playground).
2. Выберите PHP для анализируемого кода и редактор собственного правила. Названия кнопок могут отличаться: ориентируйтесь на поля кода, правила и запуск проверки.
3. Скопируйте весь код Low из **View Source** в поле кода. Не копируйте номера строк, HTML-разметку окна или подписи интерфейса.
4. В поле правила вставьте YAML ниже.
5. Запустите анализ кнопкой **Run** или её аналогом.
6. Посмотрите список находок и подсвеченные места.

Playground получает вставленный код. Для него допустим публичный учебный код DVWA; не вставляйте туда приватные конфигурации, пароли подключения, cookie или иной закрытый код.

```yaml
rules:
  - id: lab-php-request-to-sql
    languages: [php]
    mode: taint
    severity: ERROR
    message: Untrusted request data reaches SQL. Review for CWE-89.
    metadata:
      cwe: "CWE-89: SQL Injection"
    pattern-sources:
      - pattern: $_GET[$KEY]
      - pattern: $_POST[$KEY]
      - pattern: $_REQUEST[$KEY]
    pattern-sinks:
      - patterns:
          - pattern: mysqli_query($CONNECTION, $SQL, ...)
          - focus-metavariable: $SQL
      - patterns:
          - pattern: $CONNECTION->query($SQL, ...)
          - focus-metavariable: $SQL
```

Что делает правило:

- `mode: taint` включает отслеживание движения недоверенных данных.
- `pattern-sources` обозначает значения из HTTP-запроса.
- `pattern-sinks` обозначает аргумент SQL-запроса в вызовах выполнения.
- `focus-metavariable: $SQL` фокусирует проверку на самом SQL-аргументе.

Это узкое учебное правило, а не универсальный аудит всех SQL API. Для него специально не задано «очищение» по простым преобразованиям: возможную находку нужно проверить кодревью, а не считать автоматически доказанной эксплуатацией.

Основа правила: [Semgrep — taint analysis](https://semgrep.dev/docs/writing-rules/data-flow/taint-mode/overview).

### 3.3. Разберите находку

Ожидается предупреждение в месте выполнения SQL-запроса. Если вставлен весь файл с MySQL- и SQLite-ветками, находок может быть несколько. Количество находок само по себе не является критерием выполнения.

Для каждой относящейся к заданию находки запишите:

1. Название правила.
2. Файл: `vulnerabilities/sqli_blind/source/low.php`.
3. Строку получения `id`.
4. Строку формирования SQL.
5. Строку выполнения запроса.
6. Почему значение из браузера может изменить структуру SQL.

Если интерфейс показывает трассу данных, сохраните её вместе с находкой. Если трасса не отображается, покажите эти три места на скриншоте кода и объясните переходы самостоятельно.

Отсутствие находки сначала проверьте технически: PHP ли выбран, весь ли код вставлен, правильно ли сохранены отступы YAML, есть ли в коде предусмотренный правилом вызов. Не подменяйте результат анализатора скриншотом ручной инъекции.

### 3.4. Необязательный локальный вариант

Если нужно сохранить результат в JSON, сохраните правило в `lab-tools/sql-injection.yml`. При установленном Docker запустите из корня проекта:

```powershell
$LabRoot = (Get-Location).Path
docker run --rm --mount "type=bind,source=$LabRoot,target=/src,readonly" -w /src semgrep/semgrep semgrep scan --config /src/lab-tools/sql-injection.yml --metrics=off --dataflow-traces /src/vulnerabilities/sqli_blind/source/low.php
```

Чтобы получить JSON в стандартном выводе, добавьте `--json`. Локальный запуск не требует отправки исходников в Playground. Правило должно существовать до запуска команды.

Документация запуска: [Semgrep — running rules](https://semgrep.dev/docs/running-rules).

Если преподаватель отдельно требует SonarQube, согласуйте использование Semgrep либо выполните проверку в требуемой редакции SonarQube. Нельзя писать о результате SonarQube, если фактически был запущен другой анализатор. Доступность security-правил зависит от редакции и конфигурации продукта.

### 3.5. Что включить в отчёт

- Скриншот PHP-кода.
- Текст использованного правила.
- Скриншот фактической находки анализатора.
- Цепочку: HTTP-параметр → построение SQL → выполнение запроса.
- Объяснение, что проблема относится к CWE-89.
- При локальном запуске — сохранённый вывод или JSON, без секретов.

Контроль готовности: уязвимость связана с конкретным участком кода и результатом статического инструмента, а не только с поведением формы.

## 4. Задание 2. Кодревью и выявление слабых мест

### 4.1. Зафиксируйте контекст

В начале анализа укажите:

- модуль **SQL Injection (Blind)**;
- уровень **Low**;
- GET-параметр `id`;
- MySQL-ветку обработчика;
- состояние файла: исходный, ещё не исправленный.

DVWA уже имеет штатную авторизацию. Не делайте необоснованный вывод, что в приложении «вообще нет входа»: проблема рассматриваемого обработчика — обработка SQL-параметра после входа.

### 4.2. Опишите слабые места

| Наблюдение в коде | Почему это важно | Что требуется изменить |
|---|---|---|
| Значение `id` приходит из HTTP-запроса | Клиент может прислать строку, а не только число | Проверять тип, допустимый формат и диапазон |
| Значение вставляется в строку SQL | Данные могут превратиться в SQL-операторы | Использовать подготовленный запрос и привязку параметра |
| Запрос выполняется как готовая строка | СУБД разбирает введённые символы как часть команды | Отделить структуру команды от значений |
| Ответ различается при наличии и отсутствии строк | Различие используется как логический канал Blind SQLi | Устранить возможность менять условие, а не просто скрыть сообщение |
| Ошибки СУБД могут выводиться пользователю | Ошибка способна раскрыть детали реализации | Показывать нейтральный ответ, подробности писать в серверный журнал |
| Права пользователя БД могут быть избыточными | Потенциальный ущерб зависит от доступных операций | Применять минимальные права к рабочей учётной записи |

Последний пункт — рекомендация проверить конфигурацию, а не факт, установленный по одному `low.php`. Так же нельзя без проверки приписывать этому файлу отсутствие HTTPS, резервного копирования или иных свойств всей системы.

### 4.3. Объясните механизм на контрольной паре

Пусть обработчик подставляет введённое значение внутрь условия вида:

```sql
WHERE user_id = '<значение id>'
```

Для обычного `1` получится:

```sql
WHERE user_id = '1'
```

Для `1' AND '1'='1`:

```sql
WHERE user_id = '1' AND '1'='1'
```

Для `1' AND '1'='2`:

```sql
WHERE user_id = '1' AND '1'='2'
```

Первое дополнительное условие истинно, второе ложно. При существующей исходной записи изменяются результат запроса и ответ страницы.

Это и есть **boolean-based blind SQL injection**: содержимое результата SQL может не выводиться напрямую, но истинность условия определяется по наблюдаемому ответу. В данном модуле признаками служат текст сообщения и, в обычной реализации Low, HTTP-статус.

Только ошибка на одиночном апострофе ещё не является полным доказательством. Контрольная пара и анализ кода дают более убедительное объяснение причины.

### 4.4. Сформулируйте меры защиты

Главная мера — параметризовать SQL. Проверка числового ID дополняет защиту и задаёт ожидаемый формат данных, но не заменяет разделение SQL и параметров.

Также необходимы:

- обработка ошибок без раскрытия деталей клиенту;
- минимально необходимые права БД;
- корректное кодирование выводимых значений в HTML;
- повторные проверки после исправления.

Скрытие сообщений об ошибках не исправляет SQL-инъекцию. CSRF-токен тоже не заменяет параметризацию. HTML-кодирование решает другую задачу — безопасный вывод в HTML, а не построение SQL.

При желании откройте **View Source** для уровня Impossible и сравните подходы. После просмотра верните Low, если динамические проверки исходного варианта ещё не выполнены. Переключение на Impossible — демонстрация встроенного уровня, а не ваше исправление задания 3.

### 4.5. Материалы для отчёта

### 5.3. Замените код обработчика

Откройте `vulnerabilities/sqli_blind/source/low.php` в редакторе. **Полностью замените** содержимое кодом ниже, а не добавляйте его после старого. Сохраните файл как UTF-8 без BOM.

Код предназначен для MySQL/MariaDB и для подключения штатной страницей DVWA. Его нельзя открыть напрямую как самостоятельную страницу: необходимые переменные, соединение и проверку авторизации подготавливает приложение.

```php
<?php

// This file is included by DVWA's authenticated sqli_blind/index.php.
// Supported database: MySQL/MariaDB. It is not a standalone page.
if (!isset($_GET['Submit'])) {
    return;
}

$rawId = $_GET['id'] ?? null;
if (!is_string($rawId)) {
    http_response_code(400);
    $html .= '<pre>Invalid ID: enter a positive integer.</pre>';
    return;
}

$id = filter_var($rawId, FILTER_VALIDATE_INT, [
    'options' => ['min_range' => 1, 'max_range' => 2147483647],
]);
if ($id === false) {
    http_response_code(400);
    $html .= '<pre>Invalid ID: enter a positive integer.</pre>';
    return;
}

if ($_DVWA['SQLI_DB'] !== MYSQL) {
    http_response_code(500);
    $html .= '<pre>This example requires MySQL/MariaDB.</pre>';
    return;
}

$stmt = null;
try {
    $db = $GLOBALS['___mysqli_ston'];
    $stmt = $db->prepare(
        'SELECT first_name, last_name FROM users WHERE user_id = ? LIMIT 1'
    );
    if ($stmt === false) {
        throw new RuntimeException('Could not prepare lookup.');
    }

    if (!$stmt->bind_param('i', $id) || !$stmt->execute() || !$stmt->store_result()) {
        throw new RuntimeException('Could not execute lookup.');
    }
    if (!$stmt->bind_result($firstName, $lastName)) {
        throw new RuntimeException('Could not bind lookup result.');
    }

    $found = $stmt->fetch();
    if ($found === false) {
        throw new RuntimeException('Could not fetch lookup result.');
    }

    if ($found === null) {
        http_response_code(404);
        $html .= '<pre>User ID is MISSING from the database.</pre>';
    } else {
        $safeFirstName = htmlspecialchars(
            (string) $firstName, ENT_QUOTES | ENT_SUBSTITUTE, 'UTF-8'
        );
        $safeLastName = htmlspecialchars(
            (string) $lastName, ENT_QUOTES | ENT_SUBSTITUTE, 'UTF-8'
        );
        $html .= '<pre>User ID exists in the database.</pre>';
        $html .= '<p>ID: ' . $id . '</p>';
        $html .= '<p>First name: ' . $safeFirstName . '</p>';
        $html .= '<p>Last name: ' . $safeLastName . '</p>';
    }
} catch (Throwable $error) {
    error_log('Safe DVWA lookup failed: ' . $error->getMessage());
    http_response_code(500);
    $html .= '<pre>Unable to process the request.</pre>';
} finally {
    if ($stmt instanceof mysqli_stmt) {
        $stmt->close();
    }
}
```

### 5.4. Что защищает этот код

1. Обработка выполняется при наличии параметра `Submit`.
2. Проверяется, что `id` — строка, а не массив.
3. Допускается положительное целое число в заданном диапазоне.
4. Структура SQL постоянна: вместо значения используется `?`.
5. `bind_param('i', $id)` передаёт ID отдельно как целочисленный параметр.
6. `LIMIT 1` ограничивает выборку одного объекта; сам по себе этот оператор не является защитой от SQLi.
7. Значения имени и фамилии кодируются перед вставкой в HTML.
8. Подробная ошибка записывается на сервере, клиент получает нейтральное сообщение.
9. Подготовленный запрос закрывается после обработки.

Для выполнения prepared statement не требуется ручное добавление кавычек вокруг значения. Безопасность основана на отдельной передаче данных, а не на попытке удалить опасные символы.

Объектные методы MySQLi и привязка параметров описаны в [PHP — mysqli::prepare](https://www.php.net/manual/en/mysqli.prepare.php) и [PHP — mysqli_stmt::bind_param](https://www.php.net/manual/en/mysqli-stmt.bind-param.php).

6. Щёлкните по запросу правой кнопкой → **Send to Repeater**.
7. Нажмите **Forward**, затем выключите перехват: **Intercept is off**.

Альтернатива без остановки браузера: оставьте Intercept выключенным, отправьте форму, найдите запрос в **Proxy → HTTP history** и отправьте его в Repeater.

В запросе должны сохраниться правильные Host, путь и действующая cookie:

```http
GET /vulnerabilities/sqli_blind/?id=1&Submit=Submit HTTP/1.1
Host: 127.0.0.1:4280
Cookie: PHPSESSID=<SESSION_ID>; security=low

```

Здесь cookie — только обезличенный образец. В работающем Repeater не заменяйте свою настоящую cookie на заполнитель, иначе потеряете авторизацию.

Официальная инструкция: [Burp — intercepting HTTP traffic](https://portswigger.net/burp/documentation/desktop/getting-started/intercepting-http-traffic).

### 7.3. Проверьте исходный ответ в Repeater

1. Откройте **Repeater**.
2. Нажмите **Send** для неизменённого `id=1`.
3. Посмотрите статус и тело ответа.
4. Убедитесь, что это страница Blind-модуля и сообщение о существующей записи, а не форма входа.
5. Сохраните скриншот контрольного результата.

Не изменяйте Host, путь, cookie и параметр Submit при следующем опыте. Меняется только `id`.

### 7.4. Отправьте истинное условие

Значение в обычном виде:

```text
1' AND '1'='1
```

В сырой строке HTTP-запроса используйте URL-кодирование:

```http
GET /vulnerabilities/sqli_blind/?id=1%27%20AND%20%271%27%3D%271&Submit=Submit HTTP/1.1
```

Замените только первую строку или значение параметра в редакторе. Сохраните заголовки своего запроса и используемую им версию HTTP, если Burp показывает другую.

Нажмите **Send**. На исходном Low при существующей записи ожидается положительный ответ: `User ID exists in the database.`, обычно HTTP 200.

### 7.5. Отправьте ложное условие

Обычное значение:

```text
1' AND '1'='2
```

URL-кодированный вариант:

```http
GET /vulnerabilities/sqli_blind/?id=1%27%20AND%20%271%27%3D%272&Submit=Submit HTTP/1.1
```

Нажмите **Send**. На исходном Low ожидается `User ID is MISSING from the database.`, обычно HTTP 404.

Затем повторите истинное условие, чтобы убедиться, что результат воспроизводим и различие не вызвано истечением сессии или остановкой сервера.

| Запрос на исходном Low | Условие | Ожидаемое наблюдение |
|---|---|---|
| `id=1` | Обычный поиск | Найденная запись |
| `id=1' AND '1'='1` | Истина | Найденная запись |
| `id=1' AND '1'='2` | Ложь | Запись не найдена |

Связь ответа с истинностью внедрённого SQL-условия вместе с кодревью подтверждает логическую слепую инъекцию.

Документация повторной отправки: [Burp — Repeater](https://portswigger.net/burp/documentation/desktop/getting-started/reissuing-http-requests).

### 7.6. Сравните с исправленным обработчиком

1. Верните защищённый `low.php`.
2. Проверьте обычный `id=1`: должен работать поиск и вывод объекта.
3. При необходимости повторно войдите и получите актуальный запрос.
4. Отправьте истинное и ложное условия из предыдущих шагов.
5. Сравните статусы и тела ответов.

Для предложенного исправления оба SQL-выражения являются недопустимым числовым ID и получают HTTP 400 с `Invalid ID`. Они больше не управляют условием SQL.

Дополнительно отправьте:

```http
GET /vulnerabilities/sqli_blind/?id%5B%5D=1&Submit=Submit HTTP/1.1
```

Ожидается HTTP 400 без сообщения PHP о некорректном типе данных.

### 7.7. Сохраните доказательства

- Скриншот контрольного запроса и ответа.
- Скриншоты истинного и ложного условий на исходном коде.
- Аналогичную пару на исправленном коде.
- Таблицу параметров, статусов и наблюдаемых сообщений.
- При необходимости — сырой HTTP-запрос для повторного запуска sqlmap.

Для отчёта скройте значения `PHPSESSID` и других токенов, но оставьте видимыми названия параметров, тестовое значение, статус и сообщение ответа.

В Community Edition этот опыт является **ручной проверкой с Proxy и Repeater**, а не запуском автоматического Burp Scanner. Не указывайте автоматическое сканирование, если оно не выполнялось.

Временный проект не следует считать постоянным архивом результатов. Сохраните нужные материалы до закрытия Burp.

Замените «заполнить» реальными данными. Не переносите ожидаемые статусы автоматически в графу фактических.

Используйте такую подпись только если соответствующий результат действительно получен.

### 8.3. Проверка готовности

- [ ] Везде исследуется один и тот же модуль Blind SQL Injection.
- [ ] Статический анализатор действительно запущен, а находка связана с кодом.
- [ ] Кодревью объясняет, как HTTP-данные попадают в SQL.
- [ ] Исправлен исполняемый обработчик, а не только переключён уровень DVWA.
- [ ] Нормальный поиск после изменения работает.
- [ ] Некорректные типы и SQL-выражения обрабатываются без раскрытия ошибок.
- [ ] sqlmap проверил исходный вариант с действующей сессией.
- [ ] В Burp сохранена воспроизводимая пара истинного и ложного условий.
- [ ] Повторные проверки относятся к исправленному коду и не используют старый результат sqlmap.
- [ ] Из материалов удалены сессионные cookie, токены и персональные пути.
- [ ] Выводы соответствуют наблюдениям и не обещают безопасность всего DVWA.

## 9. Примеры выводов к лабораторной работе

Ниже — образцы для отчёта при успешном выполнении соответствующих экспериментов. Скорректируйте названия инструментов и формулировки под свои результаты. Если опыт не выполнен или подтверждение не получено, нельзя заявлять его как завершённый.

1. **Вывод по заданию 1.** В ходе статического анализа обработчика модуля SQL Injection (Blind) на уровне Low выявлена передача недоверенного GET-параметра в SQL-запрос. Анализатор указал участок, в котором пользовательское значение участвует в построении выполняемой команды. Полученная находка подтверждена изучением цепочки «получение параметра — формирование запроса — выполнение» и отнесена к классу CWE-89.

2. **Вывод по заданию 2.** Кодревью показало, что основная причина уязвимости — непосредственная вставка пользовательского ввода в текст SQL без параметризации. Различие ответов при истинном и ложном условиях позволяет наблюдать результат логической слепой SQL-инъекции. Определены необходимые меры защиты: подготовленные запросы, проверка формата параметров, безопасная обработка ошибок и ограничение прав доступа к БД.

3. **Вывод по заданию 3.** Существующий обработчик поиска переработан с использованием подготовленного запроса и отдельной привязки целочисленного параметра. Дополнительно реализованы проверка типа и диапазона ID, безопасный вывод сведений об объекте и нейтральная обработка ошибок. Испытания показали, что обычный поиск сохраняет работоспособность, а некорректные значения и SQL-выражения отклоняются. Изменение устраняет рассмотренный путь внедрения SQL в данном обработчике, но не исправляет остальные учебные уязвимости DVWA.

4. **Вывод по заданию 4.** Проверка исходного обработчика инструментом sqlmap подтвердила уязвимость GET-параметра `id` к boolean-based blind SQL injection. После изменения обработчика повторная проверка с действующей сессией и очисткой сохранённых результатов не подтвердила эту инъекцию в пределах применённого набора тестов. Результат сопоставлен с нормальной работой поиска и ручными испытаниями; отсутствие находки не рассматривается как доказательство полной безопасности приложения.

5. **Вывод по заданию 5.** С помощью Burp Proxy и Repeater воспроизведены запросы с истинным и ложным SQL-условиями. На исходном коде получено различие ответов, связанное с результатом внедрённого условия. После исправления оба выражения отклоняются как недопустимый ID, тогда как обычный числовой поиск выполняется успешно. Эксперимент продемонстрировал применение ручного анализа HTTP-запросов для выявления уязвимости и проверки изменения.

6. **Таким образом, общий вывод по всей работе.** В ходе практической работы исследован полный цикл работы с SQL-инъекцией: обнаружение статическим анализом, объяснение причины кодревью, динамическое подтверждение, исправление и повторное тестирование. Установлено, что надёжная защита исследуемого запроса основывается на разделении SQL-команды и пользовательских данных с помощью параметризации. Совместное применение анализа кода и проверок поведения позволяет обоснованнее оценить результат исправления, чем использование одного инструмента. Все эксперименты проведены в пределах локального учебного стенда.

Если инструмент не подтвердил уязвимость, используйте фактическую формулировку, например:

> Проверка sqlmap выполнена, однако подтверждение SQL-инъекции в данном запуске не получено. Для интерпретации результата необходимо проверить состояние обработчика, действительность сессии и доступность контрольного запроса. Этот результат сам по себе не позволяет сделать вывод о безопасности приложения.

Если повторная проверка после исправления ещё не выполнена, удалите из соответствующего вывода утверждение о её результате.

## 10. Частые проблемы

| Симптом | Причина или проверка |
|---|---|
| DVWA не открывается | Проверьте запуск веб-сервера, СУБД и выбранный порт; при Compose используйте `docker compose ps` и `docker compose logs --tail 60` |
| После входа отображается не тот модуль | Нужен путь `/vulnerabilities/sqli_blind/`, а не `/vulnerabilities/sqli/` |
| Контрольные SQL-значения не меняют ответ | Проверьте Low, исходное состояние файла, существование выбранного ID и прямой апостроф |
| Открыт HTML, а не PHP | Используйте кнопку DVWA `View Source`, не Ctrl+U |
| Semgrep сообщает ошибку правила | Проверьте YAML-отступы, наличие `rules:`, выбор PHP и отсутствие лишних символов |
| Semgrep не нашёл проблему | Проверьте полный исходник, наличие sink из правила и состояние кода; узкое правило может не покрыть иной API |
| Браузер Burp ждёт бесконечно | Запрос задержан перехватом: нажмите Forward или выключите Intercept |
| Repeater возвращает страницу входа | Обновите сессию в браузере Burp и используйте новый запрос с актуальной cookie |
| sqlmap анализирует вход, а не поиск | Проверьте URL, действующий PHPSESSID и положительный контрольный ответ |
| sqlmap выдаёт 404 | Для ложного Blind-условия это ожидаемо; для обычного существующего ID выясните причину |
| Python не найден | Проверьте установку Python 3, новый терминал и доступный вариант запуска `python` либо `py -3` |
| Не найден sqlmap.py | Проверьте текущую папку и вложенность распакованного репозитория |
| Изменение PHP не видно в браузере | Проверьте реальный обслуживаемый проект, подключение кода в контейнер и отсутствие старого ответа; при необходимости проверьте настройки кеширования PHP |
| После замены возникает HTTP 500 | Проверьте PHP-синтаксис и серверный журнал; убедитесь в MySQL/MariaDB и подключении файла штатной страницей |
| После исправления sqlmap повторяет старую находку | Используйте `--flush-session`, отдельную папку результатов и убедитесь, что исполняется новая версия кода |
| После исправления оба SQL-условия дают 400 | Для данного обработчика это ожидаемая проверка недопустимого числового ID |
| Обычный поиск тоже отклоняется | Проверьте положительный целочисленный ID, наличие Submit и корректность запроса; не считайте отказ всей страницы доказательством защиты |
| В материалах видны cookie | До публикации замените значения на заполнители, сохранив названия параметров и полезную нагрузку |

Не удаляйте базы, тома и чужие контейнеры для обычной диагностики. Не выполняйте сброс всего Docker или всего репозитория, чтобы вернуть один учебный файл.
