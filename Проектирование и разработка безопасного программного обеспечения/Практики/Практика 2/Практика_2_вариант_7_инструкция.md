## 2. Что исследуется в этом варианте

Вариант 3 содержит **уязвимость форматной строки**, CWE-134. Ключевая ошибка:

```c
printf(argv[1]);
```

Первый аргумент `printf` является форматом вывода. Программа отдаёт управление этим форматом пользователю, который задаёт аргумент командной строки.

Разница:

```c
printf(argv[1]);        /* User input is interpreted as a format. */
printf("%s", argv[1]);  /* User input is printed as text. */
```

Например, последовательность `%%` в формате превращается в один знак процента. Спецификаторы вроде `%p` требуют соответствующих дополнительных аргументов. В исходном вызове их нет, поэтому такие запросы приводят к **неопределённому поведению**: возможны вывод посторонних значений, аварийное завершение и другие эффекты, зависящие от сборки.

Это не та же ошибка, что запись длинной строки за пределы массива. В этом варианте:

- аргумент командной строки не копируется в `buffer`;
- `fgets(buffer, sizeof(buffer), secret)` ограничивает чтение размером массива;
- для массива из 32 байт читается не более 31 символа плюс завершающий нуль;
- ошибка находится в использовании пользовательского текста как формата `printf`.

В лекции есть общий пример переполнения с перезаписью адреса возврата. Для своего варианта не нужно подменять исходную программу этим примером, добиваться перезаписи возврата или вводить длинную строку только ради падения.

Классификация и принцип исправления: [MITRE CWE-134](https://cwe.mitre.org/data/definitions/134.html).

```c

int main(int argc, char *argv[]){
```

## 5. Подготовьте локальную уязвимую программу

Содержимое `variant7_vuln.c`:

```c
#include <stdio.h>

int main(int argc, char *argv[])
{
    if (argc != 2) {
        fprintf(stderr, "Usage: %s <text>\n", argv[0]);
        return 2;
    }

    FILE *secret = fopen("lab-secret.txt", "r");
    if (secret == NULL) {
        perror("fopen");
        return 1;
    }

    char buffer[32] = {0};
    if (fgets(buffer, sizeof(buffer), secret) == NULL) {
        fputs("Could not read the test marker.\n", stderr);
        fclose(secret);
        return 1;
    }

    printf(argv[1]);

    if (fclose(secret) == EOF) {
        perror("fclose");
        return 1;
    }
    return 0;
}
```

1. Вместо файла challenge-среды открывается локальный файл с тестовым маркером.

3. Добавлены проверки открытия, чтения и закрытия файла.
4. Массив инициализируется нулями.
5. Ошибка `printf(argv[1])` **специально сохранена** для исследования.

## 6. Пункт 1. Динамическое исследование

### 6.1. Начните с воспроизводимой проверки формата

Выполните:

```bash
./variant7_vuln 'LAB-%%-END'
```

Ожидаемый вывод:

```text
LAB-%-END
```

Ввод содержал два процента, а вывод содержит один. Значит, пользовательская строка интерпретируется как формат, а не выводится буквально.

Здесь нет отсутствующего дополнительного аргумента: `%%` является самостоятельной допустимой последовательностью. Это удобный стабильный тест самого механизма обработки формата, но он ещё не демонстрирует утечку конкретного секрета.

Сохраните скриншот команды и вывода.

### 6.2. Покажите последствия запроса отсутствующих аргументов

Только на своей учебной программе выполните:

```bash
./variant7_vuln '%p %p %p %p'
```

Вместо буквального текста программа обычно выводит значения в представлении указателей, иногда `(nil)`. Точные значения не фиксированы. Возможны аварийное завершение и иные проявления неопределённого поведения.

Почему: каждый `%p` ожидает аргумент соответствующего типа, но вызов `printf(argv[1])` этих аргументов не передаёт.

Не пишите, что все выведенные значения являются действительными адресами, что уже прочитан файл с паролем или что вывод всегда идёт только со стека. На x86-64 аргументы и их получение связаны также с регистрами и правилами ABI.

Для выполнения этой работы не требуется запуск оболочки, перезапись адреса возврата или извлечение настоящих секретов. Случайное падение тоже не является обязательным критерием успеха.

В комплектном `variant7_vuln.c` вызов `printf` расположен на строке **23**. Если изменяли код, сначала найдите свой номер строки:


Затем:


Что нужно увидеть:

- выполнение остановлено до `printf`;
- размер `buffer` равен 32 байтам;

Маркер в памяти подтверждает выполнение чтения файла. Сам по себе просмотр `buffer` через GDB не является эксплуатацией форматной строки: отладчик имеет разрешённый доступ к памяти отлаживаемой программы.

## 7. Как объяснить механизм

`printf` имеет сигнатуру с переменным числом аргументов:

```c
int printf(const char *format, ...);
```

В нормальном случае формат задаёт разработчик:

```c
printf("Message: %s", text);
```

Формат `Message: %s` определяет один строковый аргумент, и он действительно передан.

В уязвимом варианте:

```c
printf(argv[1]);
```

программа передаёт только формат. Если пользователь поместил в него спецификаторы, требующие аргументов, `printf` попытается получить отсутствующие значения. Это нарушает правила вызова и приводит к неопределённому поведению.

Возможные последствия CWE-134 включают раскрытие данных, аварийное завершение и, при определённых условиях, повреждение памяти. **Наличие всех этих последствий в конкретной сборке данной работой не доказывается**. В своём отчёте отделяйте потенциальные последствия от реально воспроизведённых.

Документация функции: [GNU C Library — formatted output](https://sourceware.org/glibc/manual/latest/html_node/Formatted-Output-Functions.html).

## 8. Пункт 2. Кодревью исходника из PDF

### 8.1. Таблица слабых мест

| Фрагмент | Проблема | Последствие | Исправление |
|---|---|---|---|
| `printf(argv[1])` | Внешние данные используются как формат | Неожиданная интерпретация спецификаторов, возможная утечка и иное неопределённое поведение | `printf("%s", argv[1])` или `fputs(argv[1], stdout)` |
| Обращение к `argv[1]` без проверки `argc` | Аргумент может отсутствовать | Недопустимое использование указателя, возможный сбой | Проверить число аргументов до обращения |
| `fopen(...)` без проверки результата | Файл может отсутствовать или быть недоступен | `fgets` получает некорректный поток | Проверить `secret == NULL` |
| `fgets(...)` без проверки результата | Чтение может завершиться ошибкой или EOF | Нельзя считать массив заполненным корректной строкой | Проверить возвращённое значение |
| Загрузка потенциально чувствительной строки в память | Повышает возможный ущерб от утечки памяти | Секрет может оказаться доступным при другой ошибке | Не загружать секрет без необходимости, сокращать область и время использования |
| Жёстко заданный путь challenge-среды | Код привязан к окружению | Локальный опыт падает до интересующего участка | Использовать документированный локальный тестовый ресурс |
| `fclose` без проверки | Ошибка закрытия не обрабатывается | Программа не сообщает об ошибке ввода-вывода | Проверить результат там, где это значимо |

Главная находка — CWE-134, а не сам факт существования массива `buffer[32]`.

### 8.2. Что не нужно объявлять ошибкой

- Нельзя утверждать, что `fgets(buffer, sizeof(buffer), secret)` записывает больше 32 байт: переданная граница соответствует массиву.
- Нельзя объявлять любое наличие `printf` уязвимостью: важен источник строки формата и соответствие аргументов.
- Инициализация массива нулями не исправляет небезопасный формат.
- Увеличение размера массива не устраняет эту ошибку.
- Замена на `snprintf(out, sizeof(out), argv[1])` без постоянного формата сохраняет проблему.
- ASLR, NX и защита стека не заменяют исправление вызова `printf`.

### 8.3. Пример текста кодревью

> В программе пользовательский аргумент командной строки передаётся первым аргументом printf и становится строкой формата. В результате введённые спецификаторы обрабатываются как инструкции форматирования. При наличии спецификаторов, требующих не переданные программе аргументы, возникает неопределённое поведение. Ошибка относится к CWE-134. Дополнительно отсутствуют проверки количества аргументов, открытия файла и результата чтения. При этом чтение в buffer ограничено его размером, поэтому прямое переполнение данного массива через fgets в представленном фрагменте не установлено.

Это аналитический вывод по коду. К нему добавьте собственные наблюдения динамической проверки.

## 9. Пункт 3. Исправление

### 9.1. Минимальная правка

Замените:

```c
printf(argv[1]);
```

на:

```c
printf("%s", argv[1]);
```

Альтернатива для простого текстового вывода:

```c
fputs(argv[1], stdout);
```

Теперь формат постоянный, а строка пользователя передаётся как данные. Символы `%p`, `%s` и другие последовательности внутри этих данных не обрабатываются повторно.

Одной этой правки достаточно для устранения исследуемого использования внешнего формата, но для надёжного запуска нужны и проверки ошибок из кодревью.

### 9.2. Полный исправленный код

Содержимое `variant7_fixed.c`:

```c
#include <stdio.h>

int main(int argc, char *argv[])
{
    if (argc != 2) {
        fprintf(stderr, "Usage: %s <text>\n", argv[0]);
        return 2;
    }

    FILE *secret = fopen("lab-secret.txt", "r");
    if (secret == NULL) {
        perror("fopen");
        return 1;
    }

    char buffer[32] = {0};
    if (fgets(buffer, sizeof(buffer), secret) == NULL) {
        fputs("Could not read the test marker.\n", stderr);
        fclose(secret);
        return 1;
    }

    printf("%s", argv[1]);

    if (fclose(secret) == EOF) {
        perror("fclose");
        return 1;
    }
    return 0;
}
```

В примере чтение искусственного маркера сохранено, чтобы сравнивать одинаковую структуру двух программ. Для реального приложения, которому эта строка не нужна, правильнее вообще убрать ненужную загрузку секрета.

### 9.3. Соберите исправленную программу

```bash
gcc -std=c11 -g3 -O0 -fno-omit-frame-pointer -Wall -Wextra -Wformat=2 -Wformat-security -Werror=format-security variant7_fixed.c -o variant7_fixed
```

Ожидается успешная сборка без предупреждения об исследуемом вызове.

Покажите, что такие же строгие требования выявляют сохранённую ошибку:

```bash
gcc -std=c11 -Wall -Wextra -Wformat=2 -Werror=format-security variant7_vuln.c -o variant7_check
```

Для уязвимого исходника ожидается ошибка компиляции. Это демонстрация защиты на этапе сборки, а не отдельный запуск SonarQube или PVS-Studio.

### 9.4. Проведите сравнение

```bash
./variant7_fixed 'Hello, laboratory!'
./variant7_fixed 'LAB-%%-END'
./variant7_fixed '%p %p %p %p'
./variant7_fixed '%s'
./variant7_fixed '%n'
./variant7_fixed
```

Ожидаемые результаты:

| Проверка | Уязвимый локальный вариант | Исправленный вариант |
|---|---|---|
| Обычный текст | Вывод текста | Такой же текст |
| `LAB-%%-END` | `LAB-%-END` | `LAB-%%-END` |
| `%p %p %p %p` | Неопределённое поведение, обычно посторонние значения | Буквальный текст `%p %p %p %p` |
| `%s` | В этой инструкции не требуется запускать | Буквальный текст `%s` |
| `%n` | В этой инструкции не требуется запускать | Буквальный текст `%n` |
| Нет аргумента | Сообщение Usage, код 2 в локальной адаптации | Сообщение Usage, код 2 |
| Нет файла маркера | Обработанная ошибка в локальной адаптации | Обработанная ошибка |

Тесты `%s` и `%n` здесь предназначены **для исправленного** варианта; не переносите их автоматически на уязвимую программу.

Чтобы проверить код завершения, выполните сразу после нужной команды:

```bash
echo $?
```

Успешный запуск возвращает 0, отсутствие аргумента — 2. Для проверки отсутствия файла запустите программу из другой пустой учебной папки с обычным текстовым аргументом; ожидается ошибка открытия и код 1. Не удаляйте чужие файлы для такого опыта.

Если программа не выводит перевод строки, запуски могут визуально склеиться. Для скриншота удобнее отправлять по одной команде.

Проверьте различие исходников:

```bash
diff -u variant7_vuln.c variant7_fixed.c
```

Должна отличаться только строка вызова `printf`.

### 10.3. Примеры выводов

Используйте формулировки о результатах только после их фактического получения.

1. **По динамической отладке.** Исследован обработчик пользовательского аргумента командной строки. Установлено, что исходный вызов printf интерпретирует пользовательский ввод как строку формата. Это продемонстрировано преобразованием последовательности процентов и подтверждено пошаговым выполнением программы в GDB. Если выполнялся опыт с указателями, отдельно описан его фактический результат без предположений о прочитанных секретах.

2. **По кодревью.** Основной недостаток программы классифицирован как CWE-134: использование внешне управляемой строки формата. Дополнительно выявлено отсутствие проверок аргументов, открытия и чтения файла. Прямое переполнение массива через представленный вызов fgets не установлено, поскольку размер чтения ограничен размером массива.

3. **По исправлению.** Пользовательская строка передаётся как аргумент постоянного формата, а не как сам формат. Добавлены проверки условий запуска и ошибок работы с файлом. Повторные тесты показали буквальный вывод форматных последовательностей и сохранение обычного текстового вывода.

4. **Общий вывод.** В ходе работы выполнены динамическое исследование, кодревью и исправление ошибки форматной строки. Показана необходимость различать виды бинарных уязвимостей и устранять установленную причину, а не применять меры от другого класса ошибок. Проверки компилятора и повторные испытания дополняют анализ кода; вывод об исправлении относится к исследованному фрагменту и выполненным тестам.

Если отладка ещё не выполнена, не пишите «подтверждено в GDB» или «тесты показали». Укажите фактическое состояние работы.

## 11. Частые ошибки

| Симптом | Что проверить |
|---|---|
| Выбран вариант 2, потому что практика №2 | Номер практики и номер варианта различаются; для цифры 7 нужен вариант 3 |
| Попытка переполнить массив длинным аргументом | Аргумент не копируется в этот массив; исследуйте формат printf |
| Падение исходника до printf | В PDF нет проверки fopen, а challenge-файла обычно нет |
| Локальная программа сообщает fopen | Запускайте из папки с lab-secret.txt |
| gdb или gcc: command not found | Установите инструменты внутри учебной Ubuntu |
| Команды Linux вводятся в PowerShell | Откройте оболочку Ubuntu |
| `print` или `x/s` не найдены в Bash | Это команды GDB, вводите их после запуска отладчика |
| GDB не показывает исходники | Соберите с -g3, не удаляйте C-файлы |
| GDB останавливается не на printf | Проверьте свой номер строки и пересоберите изменённый файл |
| GDB показывает другой адрес | Это нормально: архитектура, ABI, ASLR и сборка влияют на адреса |
| После printf приглашение появляется в той же строке | В программе нет перевода строки |
| Уязвимый код не проходит строгую сборку | При -Werror=format-security это ожидаемо |
| Исправление всё ещё обрабатывает проценты | Убедитесь, что используется printf("%s", argv[1]), и запущен новый бинарный файл |
| Пытаются запускать от root | Повышенные права для опыта не нужны |
| Требуют отключить все защиты | Для демонстрации этого формата отключение защит не требуется |
